## 1 — Visual Identity: A Place of Peace, Not a Corporate Template

Honor this identity rather than inventing monumental domes and minarets. Reference the supplied real exterior and interior photos.

Design language: spiritual calm + museum-quality editorial typesetting + genuinely local community warmth. Editorial serif for hero/editorial titles; crisp contemporary sans for UI; robust Naskh-style Arabic web font for Arabic body, with honest script metrics and proper RTL. Font pairing possibilities: Fraunces or Cormorant Garamond (display), Manrope or Inter (UI), Noto Naskh Arabic or IBM Plex Sans Arabic (content). Choose coherent variable fonts and avoid loading unnecessary weights. Use working font fallbacks. Proposed tokens:

- Deep evergreen `#145B40`, pine-black `#102E28`, ivory `#F8F6F0`, chalk `#FFFFFF`, muted sage `#B8C7B5`, prayer rug navy `#17395D`, soft sand `#E8E3D7`, sparing warm brass `#C3A66F`.
- Pair clean whitespace, striking editorial photography and subtle geometric patterns inspired by Islamic architecture. **No decorative Quranic verses, or Quran-as-wallpaper.** Organic transitions, unobtrusive microinteraction, no noisy parallax, autoplay media, or generic AI orb aesthetics.
- Direction A: morning sunlight touching the real glass-door exterior and gentle green typography. Direction B: calm blue prayer rug texture as a restrained section motif. Direction C: understated warm wooden mihrab detail in the story section. Use actual photos if publication-ready, otherwise clearly disclosed image concepts in demo.
- Create a real, editable, recognizable scalable SVG logo that suggests the **actual local entrance inside a pointed arch**; use supplied `/assets/brand/masjid-omar-mark-proposal.svg` as **one concept**, not as approved official branding. Provide horizontal, stacked, icon, monochrome, favicon, and dark background variants. Do **not** use raster typography baked into the AI board as the final wordmark. Arabic lockup must be verified `مسجد عمر`, using actual text with RTL and language metadata wherever practical.
- Visual behavior: mobile first, bottom sticky prayer status bar (optional/accessible), large-tap prayer cards, calm motion, exquisite responsive typography. At 320, 375, 390, 768, 1024, 1440, 1920 widths no overflow or cramped text.
- A public home should **not** look exclusive in the sense of excluding visitors; it should feel specially crafted and exceptionally hospitable. Avoid emphasizing paid memberships or gated religious access.

## 5 — Supabase Data Model and Security, No Shortcuts

Use Supabase Postgres SQL migrations under `supabase/migrations/`, reversible/explicit where feasible, schema types autogenerated, indices, unique constraints, foreign keys, `created_at`, `updated_at` triggers; sample data in safe seeds, separated from production. Suggested model (adapt as needed, but preserve behavior):

- `profiles` (auth.users FK with `ON DELETE CASCADE`; minimal display name, preferred language, consent flags)
- `staff_roles` (user_id, role `admin|imam|editor|moderator`, assigned_by, assigned_at, optional revoked_at). Member is baseline for authenticated users, no privileged role on signup. **Do not trust user-provided metadata or client updates to authorize roles.** Role changes only by securely authorized admin / bootstrap.
- `site_settings`, `settings_revision`, `prayer_methods`, `iqamah_schedules`, `prayer_overrides`, `prayer_publications`, `jumuah_sessions`
- `announcements`, `programs`, `events`, `event_registrations`, `waitlist_entries`, `volunteer_opportunities`, `volunteer_inquiries`
- `questions`, `question_messages`, `question_assignment`, `faq_proposals`, `public_faq`, `question_status_history`
- `media_assets` with privacy tier/source/credit/consent/ai_disclosure flags; `display_panels`/`display_presets`
- `audit_events` immutable app-level permissioned append records for privileged changes (not a public analytics table)
- `notification_preferences` and optional outbox table; do not claim emails or SMS are sending without configured provider.

**RLS requirements:** every exposed table has `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` and explicit grants; members read/write only their own private questions/messages and registrations; imams can read/reply only authorized questions assigned to them or within explicitly allowed shared imam queue; admins have scoped management access, authenticated by server session and DB role; public can read only explicitly `published` content; user may not set `published`, role flags or `owner_id` to arbitrary IDs. Never use service/secret Supabase key in browser. Sensitive storage buckets private and signed URLs only for authorized users. Implement typed server actions/route handlers with Zod input validation, authorization on each mutation, CSRF protections appropriate to Next.js, brute force limits for login and question submission, honeypot and abuse throttles. Handle spam with server checks; no external moderation service necessary at MVP.

**Security hardening:** protect role escalation (no self-assign), sensitive data leakage via Realtime, IDOR (guessable IDs), unsafe HTML, mass assignment, SQL injection, unbounded uploads, CSRF and unsafe redirects. Never allow anonymous Q&A publication. Membership emails, personal/religious questions can be sensitive—do not track these in third-party analytics or error logs. Audit logs should store metadata, not private question text. Provide data retention/deletion policy settings and implement deletion/export request workflow. Add tests verifying no cross-user access, member cannot read answers other than own, imam role cannot edit site settings or membership roles, admin change audit, no public access to pending questions, and deleted accounts don't expose records.

Use Supabase Auth email/password or magic-link; authenticated sessions through recommended supported Supabase SSR integration. Add email verification, reset password, session refresh, logout and protected routes. `getUser()` for sensitive server auth checks (not trusting only an unverified local claim). Elevated admin role assignment must come from DB/admin secure action or an auth hook that reads protected role rows, not editable profile columns. Require MFA for staff in production or document explicit enforcement configuration where provider permits; lock down sensitive functions until staff has enrolled. Respect request to have independent **imam and admin login experiences**; distinct routes can use same underlying Supabase Auth with robust redirects/role checks. Do not make `admin` a security-through-obscurity hidden URL trick.

Use Supabase Realtime for *public approved* prayer board/announcement updates and member's **own** question thread if RLS-safe; safe fallback polling if unset, no subscription to universal questions table. Avoid overengineering.
